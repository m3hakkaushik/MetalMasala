# AI Tools for Developers · [L42]

This document records the evaluation, deployment, practices, and governance of AI developer tools used by the engineering team during the creation of **Metal मसाला**.

---

## 1. Tool Taxonomy & Team Allocation

| Tool / Assistant | Primary Use Case in Metal मसाला | Observed Strengths | Observed Failure Modes |
|---|---|---|---|
| **Google Gemini / Antigravity** | Full-stack scaffolding, schema design, and Mongoose aggregation pipelines | Context comprehension over large workspaces, contract-faithful types, fast generation | Occasional hallucinations on experimental Mongoose plugins; required explicit constraints on file paths |
| **Anthropic Claude (Sonnet / Opus)** | Deep architectural planning, ADR drafting, concurrency algorithm analysis | Nuanced reasoning regarding concurrency (atomic decrements and compensation), precise markdown generation | Over-engineering abstractions if not constrained by strict simplicity guidelines |
| **GitHub Copilot** | Inline code autocompletion, repetitive fixture definition, JSDoc typings | High accuracy on boilerplate repetitions, validator functions, and regex strings | Silent extrapolation of invalid parameters if variable names were ambiguous |

## 2. Phase-by-Phase Utility Assessment

### 1. Scaffolding & Project Structure (B1 / B2)
- **Where it helped:** Rapidly setting up ES Module configurations, `docker-compose.yml`, boilerplate Express route files, and Zod validator schemas.
- **Where it failed:** Tendency to install heavy third-party packages (e.g. `lodash`, `uuid`, `winston`) when Node.js 22 built-in modules (`node:crypto`, `node:fs/promises`, native `fetch`) were already superior and lighter.

### 2. Testing & Test Harnesses (B2 / B3)
- **Where it helped:** Generating parameterized `node:test` + `supertest` cases covering HTTP status codes, missing fields, and rate limiters.
- **Where it failed:** Agents frequently constructed unit tests assuming synchronous database mocks or forgot that `db:ping` needs a running MongoDB instance. Human developers had to integrate `MongoMemoryServer` to ensure 100% offline test reliability.

### 3. Database Layer & Complex Aggregations (B3)
- **Where it helped:** Structuring complex `$facet` pipelines for `/products/facets` and revenue grouping (`$dateToString`).
- **Where it failed:** Initially suggested non-atomic read-then-write updates for order creation (`const p = await Product.findById(); p.stock -= qty; await p.save()`), which creates severe race conditions under simultaneous checkout traffic. Human intervention enforced the atomic `$inc` with `{ stock: { $gte: qty } }` and compensation rollback.

### 4. Documentation & Contract Verification
- **Where it helped:** Synchronizing Mermaid diagrams with Mongoose schemas and writing execution stats comparisons.
- **Where it failed:** Writing overly generic documentation. Required strict kickoff prompts specifying team conventions and lecture milestones.

## 3. Human Review & Verification Protocols

The team adopted a strict **Trust but Verify** protocol for all AI-assisted code contributions:

1. **Contract Verification:** Every generated endpoint must match `docs/01_API_CONTRACT.md` exactly — including error codes, response envelopes (`data` and `meta`), and HTTP status codes (`409` for conflicts, `422` for validation errors).
2. **Automated Test Coverage:** Code generated by AI is never committed without automated regression tests verifying both happy paths and failure edges.
3. **Static Analysis & Linting:** Every change must pass `eslint .` without warnings.
4. **Git Diff Audit:** Developers perform a line-by-line diff review before staging commits, looking for phantom dependencies or unwanted file mutations.

---

## 4. Non-Delegation Boundaries (What We Never Delegate)

The following areas are strictly off-limits to autonomous AI generation without direct human authorization:

- **Secrets and Production Credentials:** API keys (`AI_API_KEY`, Atlas credentials) are never pasted into public LLM prompts or committed to git.
- **Authorization & Permission Rules:** Access-control matrices and ownership boundaries (`isOwner || isStaff`) must be explicitly audited by humans to prevent unauthorized privilege escalation.
- **Destructive Database Operations:** `dropCollection`, `deleteMany({})`, or destructive migrations in production environments cannot be triggered autonomously.
- **Financial & Pricing Formulas:** Core cart calculation (`calculateQuote`) and invoice totals must have human-verified pure mathematical tests.
